# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Python FastAPI backend that syncs running activities from Garmin Connect into MongoDB Atlas (database `jeanCours`) and exposes weekly training statistics (HR/power time in zone, distance, arbitrary metrics) for a frontend. Despite the folder name (`Projets/Javascript`), this repo is Python only.

## Commands

Use the project virtualenv at `.venv` (Windows layout):

```sh
.venv/Scripts/python.exe -m pip install -r requirements-dev.txt   # install deps + test deps
.venv/Scripts/python.exe main.py                                  # run API on 0.0.0.0:8000
.venv/Scripts/python.exe -m uvicorn main:app --reload             # run API with autoreload
.venv/Scripts/python.exe activity.py                              # sync Garmin -> Mongo (same as GET /garmin)
.venv/Scripts/python.exe activity.py --since 2015-01-01 --until 2025-12-31   # backfill a period (re-runs are safe; --until keeps the last sync date)
# --delay N: seconds between FIT downloads (default 1) to avoid Garmin rate limits. Running anything here touches Atlas and Garmin: ask the user first.
.venv/Scripts/python.exe setWeekData.py                           # seed week types + upsert one week (edit the dict first)
.venv/Scripts/python.exe setThresholds.py                         # store dated HR thresholds for hrTSS (edit the list first)
.venv/Scripts/python.exe -m pytest                                # run all tests
.venv/Scripts/python.exe -m pytest tests/test_mongo.py::whenGetDistance_thenSumsDistanceAndEffortPerWeekForRunsOnly   # one test
.venv/Scripts/python.exe -m pytest -k Distance                    # tests matching a name
```

No linter or formatter is configured.

## Comments

Google-style docstrings (`Args:`, `Returns:`, `Raises:`). Comment only when the code doesn't say it already. Keep it minimal, in short sentences.

## Tests

- Naming: test functions are `whenMethodName_thenWhatItDoes` (`pytest.ini` collects `when*`, not `test_*`). Each test body has three sections marked `# Given`, `# When`, `# Then`; keep the comments even when a section is empty.
- `tests/conftest.py` replaces `pymongo.MongoClient` with an in-memory mongomock client **before** `mongo` is imported, and empties all collections before each test. Tests never touch Atlas. Never import app modules in `conftest.py` above that patch.
- mongomock lacks `$isoWeek`/`$isoWeekYear`; `conftest.py` patches them in. It also patches `$group` to return no document on empty input, like real MongoDB (mongomock returns one, which hides empty-result bugs). If a new pipeline uses another unsupported operator, mongomock raises `NotImplementedError`, so patch it there the same way.
- Garmin is never called: tests `monkeypatch` the names imported into `activity` (`login`, `fetch_from_date`, `download_fit_from_id`), replace `garmin.Garmin` with the `fake_garmin` fixture in `tests/test_garmin.py`, or pass a fake client object to `fetch_from_date` / `download_fit_from_id`.
- Pin a known bug with a `@pytest.mark.xfail(strict=True)` test. Fixing the bug makes the test pass, which fails the run until the `xfail` marker is removed.

## Configuration

`.env` (gitignored) must define `MONGO_USERNAME`, `MONGO_PASSWORD`, `MONGO_URL`, `MONGO_APP_NAME`, `GARMIN_MAIL`, `GARMIN_PASSWORD`. Garmin session tokens are cached in `ressources/token` (sensitive; gitignored). garth renews the short-lived OAuth2 token from the saved OAuth1 token automatically; only when the tokens are missing or rejected (`FileNotFoundError`, `GarminConnectAuthenticationError`) does `garmin.login` fall back to email/password. Network and rate-limit errors propagate and never trigger a password login. If Garmin then asks for an MFA code, only the terminal run (`activity.py`, `interactive=True`) prompts; `GET /garmin` raises `GarminLoginRequired`, returned as 401.

## Architecture

Layering: `main.py` (routes) → `mongo.py` (data access) → `aggregation.py` (pipeline definitions). Sync path: `activity.py` → `garmin.py` + `mongo.py`.

- **Swagger:** generated by FastAPI at `/docs` (spec at `/openapi.json`). Every route declares `response_model`, `tags` and `summary`; response models live in `schemas.py`, with units in field descriptions. A new route or metric needs the same. FastAPI validates responses against these models, so a mismatch is a 500.

- **Import-time side effects:** importing `mongo.py` connects to Atlas and creates collections/unique indexes (`activities.activityId`, `weekTypes.weekTypeId`, `weeks.date`). Any module importing it (including `main.py`) needs a reachable DB.
- **Sync (`update_fit`):** logs in once via `garmin.login` and passes that client to every Garmin call, reads `configuration.lastDate` (defaults to today) unless `since` is given (`--since` backfill), fetches activities since then (garminconnect pages through them), upserts each Garmin summary, then downloads the original FIT file and merges `workoutFeel`/`workoutRpe` into the same document, then sets `lastDate` to today. Activities are stored as the raw Garmin JSON (camelCase fields like `distance`, `hrTimeInZone_1`, `startTimeLocal` converted to `datetime`).
- **Weekly aggregation contract:** weekly endpoints return **parallel arrays**, one value per ISO week, aligned with `/index` (the Monday of each week, the x-axis). Every week in the range is present: weeks without runs are `0` for sums and `null` for averages.
  - `aggregation.weekly_pipeline(activity_filter, fields, accumulator)` returns one Mongo document per week with runs, grouped on `WEEK_GROUP_ID` (`{year, week}` numbers).
  - `mongo.__weekly_arrays` builds the arrays in Python over `mongo.__weeks(activity_filter)`, which is also what `get_indexes` returns. That shared week list is what keeps endpoints aligned, so new weekly endpoints must go through `__weekly_arrays`.
  - A new weekly stat is a fields dict like `DISTANCE_FIELDS` (output name → `$project` expression, `1` for a raw field), not a new pipeline.
- **Activity filter:** `aggregation.ActivityFilter(start, end, types)` selects the activities. Weekly routes get it from the `from`/`to`/`types` query params through the `Filter` dependency in `main.py`. Bounds are widened to whole ISO weeks. Without bounds, the range is the first to the last matching run. `types` defaults to `RUNNING_TYPES` (1, 6).
- **Dates:** when turning a week key into a date, use ISO (`date.fromisocalendar`, `%G-%V-%u`, `week_monday`), never `%Y`/`%W`.
- **Dynamic metrics:** `/metricsAvgByWeek`, `/metricsSumByWeek` and `/metricsByActivity` take a repeated `metrics` query param of raw activity field names, listed with units in `docs/garmin-activity-fields.md`. `/metricsAvgByWeek` weights each run by `duration` (`aggregation.weighted_average_fields`) and ignores runs without the metric. `/metricsByActivity` (one value per run, not per week) uses its own pipeline and returns empty arrays for a week without runs.
- **Training load:** `/trainingLoad` (weekly) and `/trainingLoadByDay`.
  - `training_load.py` holds the pure math: `hr_tss` (Banister TRIMP from `duration` and `averageHR`, scaled so 1 h at LTHR = 100) and `daily_load` (CTL/ATL over 42/7 days; TSB = previous day's CTL − ATL).
  - Thresholds (`lthr`, `restingHr`, `maxHr`, `trimpA`, `trimpB`) are dated documents in `thresholds`, set by `setThresholds.py`. Each run uses the latest one on or before its day. None stored → `NoThresholds` → 409.
  - CTL/ATL always start from the first matching run in all history (warm-up), then are sliced to the requested range. Weekly CTL/ATL/TSB are the week's last day's values, up to today.
- **Week planning:** the `weeks` collection (`date`, `weekTypeId`) is joined with `weekTypes` (`weekTypeId`, `label`: Base/Récupération/Intensive/Spécifique) by `/weekTypes`. It is populated manually through `setWeekData.py`.
